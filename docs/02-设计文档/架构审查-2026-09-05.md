# 逸享荟架构审查与修复记录

## 结论与范围

现有“业务单体 + 小程序/管理端 + 独立知识库”的边界适合当前产品，不需要拆成微服务。
但审查前不能判定为健壮可靠：存在用户地址越权、订单状态注入、错误计价、商户单号冲突、
回调成功标记过早和混用 MyISAM/InnoDB 等问题。修复后仍须完成生产引擎迁移和资金流程验收。

本轮审查了安全入口、身份与权限、商品下单、活动报名、优惠券与归因、支付回调、
订单关单、知识库增量同步、构建方式及文档。重点用可复现测试验证关键问题；
没有逐屏验收所有后台页面，没有做全量依赖漏洞扫描或性能压测。

保留原有 `shop-mnp/api/index.js` 的空行改动、`generated/` 和本地依赖目录。
本次不对生产订单、退款或表结构执行写操作，也不提交小程序审核。

## 尚未完成的生产门槛和技术债

### P1：跨表事务目前不成立

2026-09-05 只读快照确认，`app_goods`、`app_goods_order_detail`、`app_goods_order_after`、
`app_activity`、`app_activity_order`、`app_pay_log`、`app_pay_refund_log`、`app_user_card`、
`app_user_gold_log` 仍为 MyISAM。订单及券表已经为 InnoDB，不能因此推导整个下单链路可回滚。
HMAC 状态修改涉及的文章/广告表也需要与审计表一致的事务语义。

`sql/commerce_transaction_engines.sql` 提供 11 张表的精确迁移与回读，尚未执行。
需要完整备份、停止业务写入及调度、检查磁盘空间、逐条 ALTER、核对引擎并测试失败回滚。
DDL 隐式提交；中途失败不能通过 ROLLBACK 撤销，必须按实际引擎继续或按完整备份恢复。
本次 schema-only 快照不可以用于恢复业务数据。

### P1：资金状态闭环仍需真实集成验收

`AppGoodsOrderServiceImpl.closeExpiredUnpaidOrders` 当前关闭本地订单并释放库存，
尚未形成“微信查单/关闭交易确认 → 本地关闭”的完整状态机。
迟到的已支付回调现在会暴露错误，但没有持久化对账任务和自动处置闭环。
不能把本轮防静默失败的修复称为自动退款或对账完成。

退款回调、主动查退款及即时退款成功路径有重复的资源释放逻辑；
并发回调/重试是否只释放一次库存仍需行锁/CAS、真实数据库及支付测试。
活动支付成功后才增加已报名人数，付费待支付单不预占名额；名额耗尽时用户可能已经付款，
需明确预占/超时释放及支付后补偿策略。这些并未在本轮冒充已解决。

### P2：需要继续收敛的设计

- `AppGoodsOrderServiceImpl` 仍接近两千行，同时负责商品、会员卡、活动支付分发及退款。
  本轮只提取新订单边界；后续宜分离支付事件处理和退款状态机，避免重写全部业务。
- `selectBestChannelCoupon` 目前按最近领取时间选券，并非按优惠金额最大值选券；
  这是现有自动选券策略的限制，必须先确定多券时的产品优先级。
- HMAC 请求签名包含 actor ID 和 scope；GET query 没有纳入签名。
  后台权限是安全边界，若要求查询条件不可改，需要与达人中心同步升级签名协议。
- 现有前端源码匹配测试不能替代行为测试或真机测试；本轮新增了实际函数执行测试，
  但不能据此宣称 UI、微信支付与领券链路全通过。
- Spring Boot 2.5 / Vue 2 属于旧技术栈。本轮没有通过联网漏洞数据库确认具体 CVE，
  不做无依据的“安全无漏洞”结论，也没有在修 Bug 时顺便进行大版本迁移。
