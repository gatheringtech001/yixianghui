# 飞书与后台字段兼容审计（2026-09-02）

## 范围与口径

- 飞书：通过开放平台字段元数据接口实时读取两个 Base，仅读取表名、字段名和字段类型，不读取业务记录。
- 后台：通过只读生产数据库结构查询核对，当前为 80 张表，其中 51 张 `app_*` 表。
- “直接”表示已有稳定字段；“派生”表示可由关系或公式计算但没有独立存储；“部分”表示语义接近但无法无损承载；“缺失”表示当前后台没有对应实体或字段。
- 飞书中一个以手机号命名的异常字段已脱敏为 `[REDACTED_PHONE_FIELD]`，建议在飞书删除或重命名，不能把手机号当字段名迁移。

## 旅居 Base 字段映射

### 客户信息表

- 直接：`客户编号 -> app_customer.customer_no`；`客户名称 -> customer_name`；`联系方式 -> link_mobile`；`来源 -> acquisition_channel`；`客户状态 -> customer_label`；`日期 -> sign_time`；`需求偏好 -> customer_goods`；`跟进记录 -> return_visit_remark`；`创建时间 -> create_time`；`创建人 -> create_by`；`最后更新时间 -> update_time`。
- 派生：`订单数量`、`累计消费金额`、`关联预订订单`，前提是新增旅居客户与订单的稳定外键。
- 部分：`负责人 -> consultant_id`，现有顾问模型没有旅居客服角色；`结算表`只能在结算实体建成后建立反向关系。
- 缺失：`主播`、`新媒体账号名`；`app_customer` 还缺 `business_line`，目前无法隔离养老与旅居的状态选项及数据权限。

### 预订订单表

- 直接：`客户名称 -> app_goods_order.contact_name`；`消费金额 -> pay_money`；`联系方式 -> contact_phone`；`入住日期 -> check_in_date`；`离店日期 -> check_out_date`；`房间数 -> goods_count`；`备注 -> remark`；`创建时间 -> create_time`；`最后更新时间 -> update_time`；`小程序订单号 -> order_no`。
- 关系：`关联基地 -> goods_id -> app_goods`；`房型 -> app_goods_order_detail.sku_id -> app_goods_sku`；`同行人数 -> app_goods_order_detail.self_goods_count`；`入住晚数 -> app_goods_order_detail.inter_count`。
- 本次补齐：`订单状态 -> app_goods_order.travel_status`，编码为待确认、已确认、已取消、已入住、已离店、已结算、退款中、已退款；退款前状态由 `travel_status_before_refund` 保存。
- 派生：`间夜数 = 房间数 × 入住晚数`。
- 缺失：`订单编号`（飞书内部业务号，不能与小程序订单号合并）、`渠道`、`关联客户`稳定外键、`客服负责人`、`服务备注`、`创建人`、`修改人`。

### 结算表

- 可从订单投影：`订单编号`、`关联客户`、`渠道`、`消费金额`、`客户名称`、`关联基地`、`订单状态`、`同行人数`、`客户联系方式`、`入住日期`、`离店日期`、`房型`、`房间数`、`入住天数`、`服务备注`、`客服负责人`、创建/修改元数据。
- 现有近似字段：`是否结算 -> app_goods_order.is_cash`，但无法表达一笔订单多次或分项结算。
- 缺失且必须建独立结算表：`备注`、`结算金额`、`结算价`、`佣金`、`利润`及上述订单快照字段。飞书的 `服务备注` 类型为人员字段，与订单表同名文本字段不一致，迁移前必须修正飞书字段类型。

### 基地表

- 部分：`基地名称 -> app_goods.goods_name`；`房型 -> app_goods_sku.sku_name`；`房间数 -> app_goods_sku.stock`；`关联预订订单 -> app_goods_order.goods_id`；`订单数量`可派生；创建/修改时间可使用 `app_goods.create_time/update_time`。
- 缺失：独立 `travel_base` 主键、`酒店名称`、结构化 `城市`、创建人、修改人、与结算记录的稳定关系。商品不能替代完整基地档案。

### 主播排期表

- 全部缺失：`排期编号`、`排班日期`、`周几`、`场次序号`、`开播时间`、`下播时间`、`时长`、`直播账号`、`关联主播`、`执行情况`、`实际开播时长`、`备注`、`备注 (1)`、两组创建/最后更新时间、`父记录`。
- 治理：重复的备注和时间字段应先在飞书合并，`父记录`属于模板残留，不应原样建库。

### 主播列表

- 全部缺失：`编号`、`主播名称`、`开播时间`、`最后更新时间`、`创建时间`、`累计带货金额`、`合作状态`、`联系方式`、`粉丝数量`、`所属平台`、`主播账号`、`日期`、`下播时间`、`时长`。
- 治理：`文本 2` 实际是日期类型的匿名字段，必须先命名再迁移。

### 新媒体账号列表

- 全部缺失：`编号`、`号码`、`抖音号`、`视频号`、`微信名`、`小红书`、`公众号`、`备注`。
- 治理：`文本 3` 是匿名文本字段，必须先命名或删除。

## 养老 Base 字段映射

### 客户档案

- 身份与归属直接映射：`客户名称 -> app_customer.customer_name`；`客户编号 -> customer_no`；`电话 -> link_mobile`；`所属站点 -> dept_id`；`养老顾问（组织内） -> consultant_id`；`客户获取渠道 -> acquisition_channel`；`客户标签 -> customer_label`；`登记日期 -> sign_time`；`备注 -> remark`。
- 回访直接映射：`是否进行回访 -> return_visit`；`沟通回访记录 -> return_visit_remark`；第一次、第二次、最近一次回访时间分别映射 `return_visit_first/second/last`。
- 基本资料直接映射：身份证号、性别、出生日期、岁数、民族、文化程度、宗教信仰、婚姻状况分别映射 `idcard/sex/birthday/age/nation/education/religion/marital`。
- 地址与家庭部分映射：`现居住地址 -> live_address`；`户口所在地 -> idcard_address`；`居住情况 -> house_type`；65 岁以上人数和行动不便人数分别映射 `family_gt65_count/family_dwalk_count`。`具体地址（XX小区X栋X单元X号房）`缺独立字段，不能与区域型现居住地址无损合并。
- 联系人直接映射：两组联系人姓名、关系、联系方式映射 `link1_*`、`link2_*`；信息提供者姓名和关系映射 `info_person_name/info_person_relation`。
- 健康直接映射：身体评估、认知症、精神疾病、躯体疾病、其他疾病、长期服药、用药说明、年度体检、慢病定期就诊、自理能力、成员评估分别映射 `health_test/disease_dementia/disease_mental/disease_body/disease_other/medication_long/medication_remark/check_up_year/chronic_disease_check/self_ability/members_evaluate`。
- 健康缺失：`意识状况`；`是否持有慢病卡`与`是否持有特病卡`目前只有一个 `have_special_card`，无法分别保存。
- 家庭照护直接映射：`子女情况 -> children`；`子女是否在当地工作 -> children_nearly`；有无照护者、数量、经验、内容、时间映射 `caregiver/caregiver_count/caregiver_experience/care_content/care_times`。
- 政策与支付直接映射：养老政策评估、养老补贴、长期护理保险、医疗支付方式、月养老金、子女补贴、需求评估报告分别映射 `elderly_care_evaluate/elderly_care_subsidy/insurance_long_care/medical_pay_method/pension_month/child_pension_month/elderly_care_report`。
- 服务需求直接映射：机构托养、综合为老服务中心、康复、医疗机构、居家、适老化智能化、中医、非医疗上门护理分别映射 `organization_care/elderly_service/rehabilitation_service/medical_institution/family_service/elderly_care_ai/chinese_medical_service/care_to_door`。
- 其他直接/部分映射：`是否购买福地 -> purchased_cemetery`；`附件 -> attach`；文本养老顾问 `-> consultant_`；`医养入住情况 -> medical_care`；`父记录 -> parent_record`；消费记录可由 `app_customer_income.customer_id` 派生；创建人/时间、修改人/最后更新时间映射审计字段。
- 治理缺口：`是否进行客户信息录入`只能部分映射 `customer_info`；`客户需求产品 -> customer_goods`；`[REDACTED_PHONE_FIELD]` 是以手机号命名的异常字段，应删除或重命名，不进入后台 schema。

### 🧾收入明细数据

- 直接：`销售内容 -> app_customer_income.product_name`；`编号 -> income_no`；`客户姓名 -> customer_id`；`服务站点 -> dept_id`；`充值金额 -> charge_amount`；`消费金额 -> purchase_amount`；`余额 -> balance`；`积分 -> score`；`成交日期 -> trade_date`；`是否结算 -> settlement`；`公司收入 -> company_income`；`管家提成 -> consultant_income`；`产品类别 -> product_type`；`供应商 -> supplier_id`；`备注 -> remark`；`养老管家 -> consultant_id`；创建/修改人和时间映射同名审计字段。
- 派生：`提成`与 `consultant_income` 语义重复，若保留公式应在后台统一计算。
- 缺失：`合同金额`、`入住日期`。
- 治理：`父记录 2` 至 `父记录 6` 是模板/公式中间字段，不应直接建业务列；迁移前需确认是否仍被公式依赖。

### 活动计划表

- 部分：`日期 -> app_activity.activity_time`；`所属站点 -> dept_id`；`地址 -> address`；`活动记录`可落 `app_attachments`，但需定义业务类型和外键。
- 缺失：`供应商（活动后填）`、`是否结算`。
- 治理：`父记录`为中间字段，不应直接迁移。

### 长护险客户跟进表

- 主后台缺独立实体。需承载：`编号`、`姓名`、`最新进度`、`跟进人`、`备注`、`收资料时间`、`性别`、`身份证号`、`代理人名字`、`代理人电话`、`关系`、`地址`、`交资料时间`、`评定等级`、`签合同日期`、`上服务日期`、`累计服务月份`、`渠道`、创建/修改审计字段。
- 治理：`父记录 2` 不应直接迁移；身份证、代理人电话和地址属于敏感数据，需独立权限与脱敏策略。

### 医养机构客户跟进表

- 主后台缺独立实体。需承载：`签约金额`、`客户姓名`、`最新进度`、`入住机构`、`消费金额`、`养老顾问`、`签合同日期`、`出院日期`、`累计服务月份`、`渠道`、`备注`、创建/修改审计字段。
- 治理：`父记录`不应直接迁移。

### 📊月度收入统计

- 可由收入明细派生：`统计期末`、`统计期初`、`统计期间`、`公司收入`、`消费金额`、`辅助列-上周期`、`辅助列-上周期收入`、`环比增长率`。
- 缺失：后台没有对应统计接口/页面；`数据维护人`不应存在于纯派生统计。
- 治理：`父记录`不应迁移。

### 养老顾问列表

- 直接/部分：`养老顾问 -> app_consultant.consultant_name`；`电话 -> mobile`；`备注 -> remark`；`创建时间 -> create_time`；`消费记录`可由收入表的 `consultant_id` 派生；`医养机构客户跟进表`待新实体建立后反向关联。
- 缺失：`日期`、`微信是否添加`、`发展人`、`是否转化`、`创建人`。

### 满意度调研

- 主后台缺独立实体。需承载全部字段：`客户名称`、`提交时间`、`产品打分`、`服务打分`、`是否考虑回购`、`是否需要申请售后？`、`其他意见和建议`、`订单编号`、`订单类型`。

## 实施优先级

1. P0：部署本次 `travel_status` 迁移与订单状态代码；随后让 AI/运营模块停止直接写飞书订单状态，改写主后台受控接口。
2. P0：为 `app_customer` 增加业务线，并为旅居订单增加渠道、旅居客户、基地、客服负责人、服务备注和审计人字段。
3. P0：新建旅居基地与旅居结算实体，结算创建必须有订单唯一约束，替代飞书“已离店即新增记录”的非幂等自动化。
4. P1：新建主播、账号、排期三张表；新建长护险跟进、医养跟进、满意度三张表。
5. P1：补齐养老客户的慢病卡、意识状况、具体地址；补齐收入合同金额和入住日期；补齐活动供应商与结算。
6. P2：月度收入统计用查询/报表实现，不复制飞书公式中间字段；清理所有 `父记录*`、`文本 2/3` 和异常手机号字段名。
